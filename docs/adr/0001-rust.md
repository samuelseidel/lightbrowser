# ADR 0001: Rust for everything we write

Status: Accepted (2026-11-02)

## Context

LightBrowser is a headless browser for internal bot-detection validation. It
has hard resource budgets (idle RSS under 15 MB, no disk writes by default,
match or beat Lightpanda on wall time, peak RSS and CPU time). It parses untrusted HTML,
CSS and network data all day, so memory-safety bugs are a real risk.

It also has to reuse existing work. The stealth-browser repo already has Rust
crates we want: `consistency/` (persona validation) and `behavior/` (human
input simulation). The SFC32 PRNG is already ported to
Rust and tested bit-for-bit against the C version.

The main dependencies we need are Rust-native or have maintained Rust bindings:
`html5ever`, `selectors`, `cssparser`, `taffy`, `tiny-skia`, `skrifa`, `hyper`,
`tokio`, `boring` (BoringSSL), the `v8` crate and Servo's `mozjs`.

## Decision

All code we write is Rust (edition 2024), in one Cargo workspace. This includes
the DOM, CSS, layout, networking, WebIDL code generator, CDP server and
persona handling.

C and C++ appear only as vendored dependencies we build and link: BoringSSL, V8
and SpiderMonkey. We do not add new C or C++ code of our own. The Python SDK
under `sdk/python` is a thin client and is not part of the browser binary.

Release builds use fat LTO, `codegen-units=1`, `panic=abort`, stripped symbols
and mimalloc.

## Alternatives considered

- **Zig** (what Lightpanda uses). Small and fast, but the library ecosystem
  for HTML parsing, CSS selectors, TLS and async I/O is thin. We would have to
  write much more ourselves, and we could not reuse the stealth-browser crates.
- **C++** (what Chromium and Gecko use). Maximum fit with V8 and SpiderMonkey,
  but no memory safety, slower to build, and a worse dependency story. We
  would give up the Rust crates above.
- **Go.** Good networking, but a garbage collector works against the RSS
  budget, and embedding V8 or SpiderMonkey through cgo is awkward and slow
  across the boundary.
- **Python or Node for parts of it.** Too much memory and startup cost for the
  budgets, and it would add a second runtime to ship.

## Consequences

- We get memory safety in all code that handles untrusted input. `unsafe` is
  limited to FFI with V8, SpiderMonkey and BoringSSL, and to a few hot paths.
- The stealth-browser `consistency/` and `behavior/` crates are vendored with
  little change (M4, M5).
- Build times are long, especially for V8 and `mozjs`. Cargo features keep the
  two engines out of each other's builds (see ADR 0006).
- Rust async (tokio) fits the thread-per-core model, where each thread owns its
  JS engine instances and nothing is shared across threads.
- Contributors need Rust experience. CI must build and lint (`cargo clippy`)
  both browser families.
- The FFI layers to the JS engines need careful review, because a bug there
  breaks the safety guarantee.
